# 模型失败诊断工作流（Diagnosis Workflow）

> 从「模型效果不好 → 换模型」升级为「效果不好 → 诊断原因 → 针对性修复 → 沉淀经验」。
>
> 本文件定义六步标准诊断流程，并接入已有的 FailureMemory / ErrorLifecycle / QualityGateway。

---

## 一、为什么需要诊断工作流

普通队伍和专家队伍在面对模型失败时的行为差异：

```
普通队伍：
  模型效果不好 → 换个模型试试 → 还是不好 → 再换 → ... → 时间耗尽

专家队伍：
  模型效果不好 → 观察现象 → 生成假设 → 验证假设 → 定位根因 → 修复 → 验证修复有效
```

**核心差异**：专家不是「试出来的」，而是「诊断出来的」。

---

## 二、六步标准诊断流程

```
Step 1: 症状识别（Symptom Recognition）
  观察到什么异常？
  → 比预期差多少？（定量）
  → 是突然出现的还是一直存在？

Step 2: 假设生成（Hypothesis Generation）
  可能的原因有哪些？
  → 从 [通用症状库] 匹配最可能的 2-3 个原因
  → 按概率排序（数据问题 > 参数问题 > 模型结构问题 > 理论问题）

Step 3: 假设验证（Hypothesis Validation）
  逐一验证候选原因
  → 设计验证实验（最小改动原则：只改一个变量）
  → 确认/排除

Step 4: 根因定位（Root Cause）
  [已确认原因]
  → 定位于：数据层 / 参数层 / 模型层 / 理论层？
  → 分类为 A/B/C/D 错误类型（对接 ErrorLifecycle）

Step 5: 修复执行（Remediation）
  针对根因应用修复
  → 修复策略（从 [对应症状文档] 获取）
  → 验证修复效果（定量对比）

Step 6: 经验沉淀（Memory Recording）
  记录本次失败
  → FailurePattern（对接 FailureMemory）
  → 写为一条治理知识（对接 QualityGateway）
```

## 三、诊断优先级原则

### 原则 1：先排除数据问题

```
数据是地基。地基有问题，建什么楼都会塌。

在怀疑模型之前，先问：
  □ 训练数据正确吗？（有没有加载错文件/选错列？）
  □ 数据划分正确吗？（时序数据是否用了随机划分？）
  □ 特征有没有泄漏？（测试集的信息是否进入了训练集？）
  □ 缺失值处理了吗？
```

### 原则 2：先跑基线再上复杂模型

```
在调试复杂的RF/LSTM之前，先跑一个最简单的基线：
  - 回归 → 均值预测
  - 分类 → 多数类预测
  - 时序 → 朴素预测（ŷ(t+1) = y(t)）

如果复杂模型比基线还差：
  → 不是数据问题，是模型实现有 bug
如果复杂模型略优于基线但远低于预期：
  → 检查特征工程和超参数
```

### 原则 3：只改一个变量

```
验证假设时，每次只改变一个变量：
  只改学习率？只改特征？只改数据划分？
→ 如果同时改多个，你不知道到底是哪个修复了问题。
```

## 四、与已有系统的对接

### 对接 FailureMemory

```python
# 诊断完成后，记录为 FailurePattern
failure_memory.add(FailurePattern(
    symptom="训练R²=0.98, 测试R²=0.35",
    root_cause="过拟合：模型复杂度远超数据可支撑程度",
    remediation="降低max_depth从None到5 + 3折交叉验证",
    verification="修复后测试R²=0.71，训练-测试差距从0.63缩至0.15",
    risk_level="medium",
    affected_models=["RandomForest", "XGBoost"],
    trigger_conditions={
        "train_test_gap": "> 0.3",
        "sample_size": "< 500"
    }
))
```

### 对接 ErrorLifecycle

| 根因层级 | Error 类型 | 回退策略 |
|:---:|:---:|------|
| 数据层 | Type A (数据问题) | 回到 S1 (问题分析)，重新审计数据 |
| 参数层 | Type B (参数问题) | 回到 S4 (求解)，重新调参 |
| 模型层 | Type C (模型选择) | 回到 S2 (模型选择)，换模型 |
| 理论层 | Type D (假设问题) | 回到 S1 (问题分析)，修改假设 |

### 对接 QualityGateway

修复后，Gateway 重新检查：
- `evidence_backed_selection`: 修复有实验验证吗？
- `overfit_check`: 训练-测试差距是否在安全范围？
- `memory_governance`: 是否有类似的历史失败记录？

## 五、诊断工具包

### 必备诊断图表

| 图表 | 用途 | 什么症状时必画 |
|------|------|---------------|
| 训练/验证 loss 曲线 | 判读过拟合/欠拟合 | 训练好测试差 / 都差 |
| 残差 vs 拟合值图 | 检查线性假设和异方差 | 模型效果差 |
| 残差自相关图(ACF) | 检查时序模型充分性 | 时序预测差 |
| 预测值 vs 真实值散点图 | 检查系统性偏差 | 模型效果差 |
| 特征重要性排序 | 检查特征是否合理 | 解释性不足 |
| 学习曲线（N vs error） | 判断是否需要更多数据 | 都差 / 训练测试差 |

### 必备诊断统计量

| 统计量 | 用途 | 正常范围 |
|--------|------|:---:|
| 训练-测试 R² 差距 | 过拟合指示器 | < 0.15 |
| 残差均值 | 检查无偏性 | ≈ 0 |
| Durbin-Watson | 检查残差自相关 | 1.5 - 2.5 |
| VIF（方差膨胀因子） | 检查多重共线性 | < 10 |
| Breusch-Pagan p | 检查异方差 | > 0.05 |

## 六、诊断报告的论文价值

诊断本身可能在论文中变成创新点：

```
❌ 失败 → 换了模型 → 效果好了
   → 评委：你就是试出来的

✅ 失败 → 诊断 → 发现失败原因 → 针对性改进 → 效果好了
   → 评委：这是有深度的研究
```

**论文表达模板**：

```
初步实验发现，[模型A] 的 [指标] 远低于预期（[值]）。
为诊断原因，本文进行了系统分析：

(1) [检查项1]：[发现]
(2) [检查项2]：[发现]
...
(N) [检查项N]：[发现]

综上，模型失效的根因在于 [根因]。
基于此诊断，本文 [修复方案]。
修复后 [指标] 从 [旧值] 改善至 [新值]。
```

## 七、与具体症状文档的衔接

```
diagnosis_workflow（本文件）
    ↓ 标准六步流程
    ↓
general_symptoms/（下一步查阅）
    ↓ 特定症状 → 候选原因 → 验证方法 → 修复策略
    ↓
prediction_diagnosis/ / optimization_diagnosis/ / ...（按需查阅）
    ↓ 模型专项诊断
    ↓
FailureMemory（经验存储）+ ErrorLifecycle（回退）+ QualityGateway（门禁）
    ↓ 治理闭环
```
